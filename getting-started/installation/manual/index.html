Manual installation

A manual installation forks the repository and deploys it with the GitHub Actions workflows it ships. You get a production instance, a staging instance, a live preview for every branch, and the end-to-end tests on every pull request.

Requirements

Section titled “Requirements”
  • A Cloudflare account on the Workers Paid plan.
  • A GitHub account for the fork.
  • For the one-time commands: a clone of your fork with Node.js 22.22 or later and pnpm 9 or later, and pnpm install run once. Wrangler comes with the repository.

What gets deployed

Section titled “What gets deployed”

All Cloudflare resources are named after the product.

TargetWorkerD1 databaseDeployed by
Productioniron-gardeniron-garden-prodA push to main
Stagingiron-garden-stagingiron-garden-stagingA push to main
PreviewA Worker Preview of iron-garden-staging, per branchiron-garden-preview-<branch>-<hash>A push to any other branch

Each target keeps its git repositories in its own Artifacts namespace, named after its database. Workers AI, the Worker Loader and the Durable Objects are bound on every target and need no setup.

1. Fork and enable the workflows

Section titled “1. Fork and enable the workflows”
  1. Fork alonbardavid/iron-garden.
  2. Open the fork’s Actions tab and enable workflows.

2. Create a Cloudflare API token

Section titled “2. Create a Cloudflare API token”

In the Cloudflare dashboard, create an account API token scoped to the one account you deploy to, with these permissions:

  • Workers Scripts: Edit
  • D1: Edit
  • Artifacts: Edit

Every deploy first checks that the token can use Artifacts and fails if it cannot.

3. Add the repository secret

Section titled “3. Add the repository secret”

In the fork, open Settings › Secrets and variables › Actions and add the token from step 2 as the repository secret CLOUDFLARE_API_TOKEN.

4. Create the production database

Section titled “4. Create the production database”

The production deploy never creates its database. Create it once from your clone:

The staging deploy creates iron-garden-staging itself.

5. Deploy

Section titled “5. Deploy”

Push to main (any commit will do). Two workflows run:

  • Staging Deploy finds or creates the staging database, applies migrations and deploys iron-garden-staging. Its first run also turns on Preview URLs for that Worker.
  • Production Deploy finds iron-garden-prod, applies migrations and deploys iron-garden.

Watch them in the Actions tab.

6. Set the setup token

Section titled “6. Set the setup token”

Each Worker reads one secret, SETUP_TOKEN: any random string of 4 or more characters, which you type once to create the first admin. Set it once the first deploy has created the Workers, for production, staging and branch previews:

The last command is for previews, which take their secrets from the staging Worker’s Previews base config when they are created, not from the staging Worker itself. Setting a secret deploys a new version of that Worker.

What each push does

EventWorkflowResult
Push to mainStaging DeployMigrates and deploys staging.
Push to mainProduction DeployMigrates and deploys production. Fails if iron-garden-prod is missing.
Push to any other branchPreview DeployDeploys the branch as its own preview and comments its URL on the pull request.
Pull request openedPreview Comment on PR OpenPosts the preview URL when the branch was pushed before its pull request existed.
Pull request, and push to mainE2E TestsBuild, type-check, lint, unit tests and the Playwright suite. Needs no secrets.
Branch deleted, and weeklyPreview TeardownDeletes the branch’s preview, database and repositories; weekly, prunes orphans.
Push to mainDocs to GitHub PagesPublishes these docs to GitHub Pages, once you turn Pages on.

How to work with previews and staging is in Developing with staging.

Deploy from your machine

Section titled “Deploy from your machine”

You can deploy production without GitHub Actions. Both commands build first and need PROD_HOST in the shell and a Cloudflare login:

pnpm run deploy does not apply migrations. Run pnpm db:migrate:remote first whenever the update adds any. The next push to main deploys over a local deploy.

For more detail on the workflows, see deployment in the contributor docs.
