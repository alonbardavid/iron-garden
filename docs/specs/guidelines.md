# Engineering guidelines

These rules apply to all code in this repo. The repo is public, so assume every line,
workflow and config is read by both contributors and attackers.

## 1. One-click deployable

- Use only resources the [Deploy to Cloudflare button](https://developers.cloudflare.com/workers/platform/deploy-buttons/)
  provisions automatically: Workers, D1, R2, Durable Objects, Queues, KV, Workers AI, AI
  Gateway, Vectorize, Hyperdrive, Secrets Store, Artifacts (a binding names a namespace,
  which Artifacts creates on first use).
- Anything that needs manual setup (email sending, a verified sender domain, a custom domain,
  third-party API keys) is **optional**. The instance must deploy and work without it, and
  degrade predictably:

  | Optional resource                            | Without it                                                                       |
  | -------------------------------------------- | -------------------------------------------------------------------------------- |
  | Email sending (`send_email` + sender domain) | No self-service sign-up or reset emails; admins create users and reset passwords |
  | Custom domain                                | Instance serves on its `workers.dev` host                                        |
  | Anthropic / OpenAI-compatible key            | AI features run on Workers AI                                                    |
  | External CI                                  | Changes have no CI checks; branch rules can still require reviews                |

- Feature detection is explicit: a single `capabilities` module reads the bindings and
  settings once and every feature asks it, rather than probing bindings ad hoc.

## 2. Minimal input from the person deploying

- Every setting has a sensible default. The deploy button should ask for as little as
  possible; target is **one** required value (`SETUP_TOKEN`, see [deployment.md](./deployment.md)).
- Secrets the app can generate itself are generated on first boot (e.g. the session-signing
  secret), never asked for.
- Everything else is configured after deploy, in the admin UI, and stored in D1.
- Resource names come from the wrangler config defaults; nothing references an account id,
  zone id or resource id in committed files.

## 3. Secure without obscurity

The code is public, so security must hold even when an attacker has read all of it.

**Secrets and credentials**

- No default, sample or fallback secret is ever accepted in a deployed instance. The local-dev
  values in `wrangler.jsonc` are refused when `NODE_ENV=production`.
- Tokens are random (≥ 256 bits), prefixed (`cgit_pat_`, `cgit_agt_`) so secret scanners can
  find leaks, shown once, and stored only as SHA-256 hashes.
- Passwords are hashed with the better-auth hasher. All secret comparisons are constant-time.
- A fresh instance cannot be claimed by whoever finds its URL first: first-admin setup
  requires `SETUP_TOKEN`, and the setup endpoint is disabled permanently once an admin exists.

**Requests**

- Authorization is checked in the domain layer (`libs/forge`), not only in routes, so every
  entry point (UI API, git HTTP, MCP, job runner) gets the same checks.
- Deny by default: a route or tool without an explicit permission check fails tests.
- Webhooks are signed with HMAC-SHA256 and a timestamp; per-hook secrets are generated by the
  instance.
- Login, token auth and git auth are rate-limited per IP and per account (Durable Object
  counter).
- Rendered user content (READMEs, comments, file views) is sanitized; no inline scripts;
  strict Content-Security-Policy.
- Provenance from commit trailers is a **claim** and is shown as such; the authenticated
  pusher (user or agent token) is the authoritative record.
- AI output (groups, classifications, impact checks) is untrusted text: it is rendered as
  data and never executed or used to decide permissions.

**GitHub repo and CI**

- Workflows declare least-privilege `permissions:` per job; default is `contents: read`.
- Third-party actions are pinned to a full commit SHA.
- Never use `pull_request_target` with a checkout of PR code. Secrets are never exposed to
  workflows triggered from forks; preview deploys run only for branches in this repo.
- `CODEOWNERS` covers `.github/`, deploy scripts and wrangler configs.
- Dependabot (or Renovate) for actions and npm; secret scanning and push protection on.
- `SECURITY.md` explains how to report a vulnerability privately.

## 4. Code shape

- **Concise.** No dead code, no speculative abstractions, no commented-out code. Prefer a
  small, mature library over hand-rolling solved problems (edge-stack convention #7), except
  inside `libs/git-core`, which is ours by design.
- **Clear domains.** Each package owns one domain and exposes a small public API from its
  `index.ts`. Cross-package imports go through that API only.
- **Enforced boundaries.** ESLint import rules encode the dependency direction:

  ```
  apps/*  →  libs/mcp  →  libs/review, libs/collab, libs/evidence  →  libs/forge  →  libs/git-storage  →  libs/git-core
                          ↘ libs/ai (optional, behind an interface)
                          ↘ libs/db-models, libs/identity
  ```

  `libs/git-core` imports nothing from the repo and nothing Cloudflare-specific. Admin code
  stays isolated as edge-stack requires.

- **Types at the edges.** Every external input (HTTP body, git protocol bytes, job payload,
  webhook, MCP call) is parsed and validated once at the boundary; internal code trusts types.
- **Comments are rare** and explain why, never what changed.
- **Green before merge.** install, type-check, lint, build, unit, interop and e2e suites
  (local and against the PR's preview) must pass.

## 5. Real tests, easy review

Full detail in [testing.md](./testing.md).

- **Real git, real Cloudflare.** Git behaviour is proven with the real `git` binary, never a
  mocked protocol; storage behaviour runs in workerd locally and on real D1, R2 and Durable
  Objects in the PR's preview. Mocks are allowed only at true external edges (third-party AI
  providers, outbound webhooks).
- **Fixtures are infrastructure.** Test repos are generated by scripts with real git,
  deterministic, committed as bundles, and checked in CI. A bug fix in the git engine comes with
  the fixture that reproduces it.
- **Scenarios are the shared language.** Every e2e test starts from a named scenario, and every
  feature ships with the scenario that shows it, so a reviewer can try it on the PR's preview
  without pushing anything.
- **Reviewer time is the scarce resource.** PRs stay small and single-purpose, the PR comment
  links straight to the affected scenarios with screenshots, and failures attach the logs
  needed to understand them.
