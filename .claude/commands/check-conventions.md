Read the file at $ARGUMENTS and verify it follows these conventions:

1. **Step-down rule**: Code should read top-to-bottom with descending levels of abstraction. The main exported component/function should be near the top of the file, with helper components and utilities below it.
2. **Single level of abstraction**: Each function or component should operate at a single level of abstraction. Specifically:
   - A component should manage at most one piece of domain logic (e.g. transcript management OR form submission, not both). Extract additional concerns into custom hooks.
   - Handler functions that do more than 2 sequential steps (validate, update state, call API, process response) should be broken up — extract the API + response processing into a hook or helper.
   - A component's render section should ideally have no more than one conditional or one iteration — extract additional ones into sub-components.
3. **Minimal comments**: Prefer descriptive function, variable and type names over prose — code should be self-documenting. TSDoc-style comments documenting parameters, return values and non-obvious contracts are acceptable. Flag comments that narrate a change that was made ("renamed from…", "now also handles…", "previously used X") — comments must describe the code as it currently stands; git history is where changes are examined. Also flag comments that merely restate what the code plainly says.
4. **Server logging**: Backend should log whenever an decision is made, new data is retrieved. We want to be able to troubleshoot effectively.
5. **Forms via @lib/ds only**: Forms must be built with the form primitives exported from `@lib/ds` (StandardForm, FormTextInput, FormPasswordInput, FormSubmitButton, FormGeneralErrors, useForm). Flag any direct import from `@mantine/form` outside of `libs/ds` — it should go through `@lib/ds` so the form library can be swapped later.
6. **Authorization in the domain**: Every access decision goes through a domain lib: repository levels through `@lib/forge` (`authorize`, `requireUser`, `requireInstanceAdmin`), sessions and pull requests through `@lib/collab` and `@lib/review`, which call forge. Admin-only API procedures are implemented on the `adminApi` implementer, never gated per handler. Flag a route handler or frontend screen that decides access itself (checks a role or level, filters rows by permission) instead of calling the domain, and flag admin pages whose server side is not on `adminApi` or better-auth's admin endpoints.
7. **Prefer small, mature libraries over hand-rolled low-level code**: For well-solved low-level functionality (date math, UUID, deep clone/equal, debounce/throttle, query-string parsing, result/option types, slugify, etc.), use a mature, industry-standard library instead of writing your own — PROVIDED its footprint is small (a few kB, ~10–20 kB gzipped max; tree-shakeable preferred). Before adding a dependency, use the `check-library-to-install` subagent (auto-delegated when a dependency decision comes up) to vet candidates (fit, docs, Snyk maturity/security, bundle size) and pick per its recommendation. Flag a new hand-rolled implementation of a well-solved low-level problem where a small mature library exists (e.g. re-implementing date arithmetic instead of a dedicated date library, a custom result-type union instead of a maintained one), and flag pulling in a heavy dependency (>~20 kB gzipped, or one with poor Snyk health/maintenance) for a small need. Trivial one-liners (a `padStart` time formatter, a lexicographic string compare) may stay inline — this is about non-trivial functionality, not banning all local helpers.
