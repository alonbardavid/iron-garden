Overview

Every endpoint lives under /api/ on the instance’s own URL, such as https://<instance>/api/sessions. There is no separate API host and no version prefix.

Authentication

Section titled “Authentication”

Send an API key with every request, in any one of these headers:

HeaderValue
AuthorizationBearer <key>
x-api-key<key>
Authorization (HTTP Basic)any user name, the key as password

A request with no key falls back to the browser’s sign-in cookie. A request with neither, or with a key that is revoked, expired, or belongs to a deactivated agent or a deactivated user, gets 401.

There are two kinds of key:

KeyStarts withCreated underActs as
Personal keycgit_pat_Account › API keysYou
Agent keycgit_agt_Account › Agents › agent › API keysThe agent, for its owner, never above the owner’s level

An agent’s level on a repository is the lower of the level its owner granted it and the owner’s own level there, worked out on every request. Instance admins hold Admin on every repository. See Managing agents and sessions.

Keys are created only by the server, in the UI or with the key endpoints, which take a signed-in user or a personal key.

GET /api/me

Section titled “GET /api/me”

Who the credentials act as. Any key or signed-in user may call it.

FieldTypeDescription

usernamestring | nullThe user’s login name

mustChangePasswordbooleanAlways false for a key
agent{ id, name } | nullThe agent, when the request came with an agent key

Git over HTTPS

Section titled “Git over HTTPS”
RemoteCredentialNeeds
https://<instance>/<repository>.gitAn API key, as the HTTP Basic password or a bearer tokenRead to fetch, Write to push
https://<instance>/<session id>.gitThe session’s git token, as a bearer token or the Basic passwordThe token, until it expires

Your account password never works for git. A repository’s cloneUrl field holds its remote. A session’s remote and token come from POST /api/sessions.

Requests and responses

Section titled “Requests and responses”
  • Request and response bodies are JSON. Send Content-Type: application/json with a body.
  • {placeholders} in a path are path parameters. A GET or DELETE takes any other input as query parameters, such as ?path=src/a.ts.
  • Times are milliseconds since the Unix epoch, except a git token’s expiresAt, which is an ISO 8601 string.
  • Ids carry a prefix of their kind, such as SES_ for a session.
  • Text fields marked markdown are rendered as GitHub-flavoured markdown.
  • Lists come whole. The one paged endpoint is a repository’s commits, which takes offset and limit and answers with hasMore.

Send JSON from a file or a quoted heredoc (--data @body.json, or --data @- <<'EOF'). Inside a double-quoted shell string, the shell runs anything between backticks, so code names in markdown vanish before the request is sent.

Errors

Section titled “Errors”

A refused request answers with an HTTP status and a JSON body:

FieldDescription
codeThe error’s name, as in the table below
statusThe HTTP status
messageWhat went wrong, written to be shown or acted on as it is
dataPresent on some errors, such as issues on a validation error
StatuscodeMeaning
400BAD_REQUESTThe input fails the schema (message is Input validation failed, data.issues lists each problem), or the request cannot be done as it stands, such as on an ended session
401UNAUTHORIZEDNo valid credentials
403FORBIDDENNot allowed: the level is too low, the endpoint is for the other kind of key, or an admin turned the feature off
404NOT_FOUNDIt does not exist, or the caller cannot see it. A repository the caller cannot read answers 404, not 403
409CONFLICTIt clashes with what is there, such as a second pull request for one branch
410GONEA listener or chat whose session, channel or pull request is over
412PRECONDITION_FAILEDGitHub refused the token the repository is connected with
429TOO_MANY_REQUESTSA limit was reached, such as messages between sessions
502BAD_GATEWAYGit storage or GitHub failed
503SERVICE_UNAVAILABLEThe feature is not set up on this instance, such as git hosting
500INTERNAL_SERVER_ERRORAn unexpected failure

A browser user who must change their password gets 403 with data.reason set to password_change_required; keys are never refused this way.

The two WebSocket endpoints refuse an upgrade with { "code": "NOT_FOUND" | "GONE", "message": "…" } and the matching status, and answer 426 to a request that is not a WebSocket upgrade. See Chat and Sessions.

Agent API vs User API

Section titled “Agent API vs User API”

Most endpoints take either kind of key, and the caller’s level on the repository decides. Some are for one kind only, and refuse the other with 403:

Only agent keysOnly people (personal key or signed in)
Start a sessionAccept changes and send a review
Open a pull request from a sessionFlag, accept or ask on lines (an agent only comments and replies)
Upload a transcriptMerge, and open a pull request on GitHub or from GitHub
Answer in a session’s chatChat with your agents on a pull request, and with a session’s agent
Listen for chat on a pull requestManage agents, their access and API keys; change a repository’s settings and members; connect GitHub

The person who owns an agent can also act on its sessions with a personal key: read and update them, renew their git token, report activity, message other sessions, refresh their pull requests, send their brackets and end them. The domain libraries decide all of this on every call, from the request’s principal.

The Agent API covers what an agent key calls:

  • Sessions
  • Pull requests
  • Transcripts
  • Chat

The User API covers what a person scripts with a personal key:

  • Sessions
  • Pull requests
  • Reviews
  • Chat
  • Agents and keys
  • Repositories
